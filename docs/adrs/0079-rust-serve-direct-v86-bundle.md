# ADR 0079: Rust Serve Direct v86 Bundle

## Status

Accepted.

## Context

Rust `wanix-rust serve` already exposes static files, the direct binary 9P
WebSocket route at `/.well-known/export9p`, and the discovery document at
`/.well-known/wanix.json`. That is the server side of a browser/v86 demo, but
the CLI's `--bundle` URL still only reported a hint: no Rust-served page
actually consumed the discovery document and handed the 9P route to v86.

The existing v86 browser library accepts `filesystem.proxy_url` and uses it as a
plain WebSocket 9P proxy. Rust serve's discovery document advertises the
matching direct binary WebSocket route, so the next useful integration proof is
route composition rather than another 9P operation.

## Decision

Make `wanix-rust serve --bundle direct-v86` serve `/?bundle=direct-v86` as a
small browser page generated by the Rust CLI. The page:

- imports the checked-in v86 browser module from `/v86/lib/mod.js`;
- fetches `/.well-known/wanix.json`;
- reads `routes.p9.websocket`;
- configures v86 with `filesystem: { proxy_url: routes.p9.websocket }`;
- uses the checked-in v86 BIOS/WASM asset paths;
- accepts kernel and initrd URLs from the page controls or query string.

Other bundle names still fall through to the static root. The generated page is
only selected when the command is configured with `--bundle direct-v86` and the
request query asks for `bundle=direct-v86`.

## Consequences

Rust serve now has a browser-facing v86 route wiring proof: the CLI can print a
bundle URL that returns a page wired to the same listener's direct 9P export.
This is a visible step toward qemu/v86 and VS Code integrations while keeping
the route contract centered on Rust serve discovery.

This does not assemble a full VM bundle, provide kernel/initrd assets, implement
the Ethernet/vnet bridge, or add browser authentication policy. Those remain
larger follow-up decisions before exposing writable host roots outside local
development.
