## USER Personas — Wanix Rust-native port

Two personas for people who want to *use* Wanix to get something done. They span the requested range: a curious newcomer who has never heard of Plan 9, and a power user wiring a personal compute mesh. Both are grounded only in shipped/demonstrated capabilities in the repo (CLI subcommands, recipes 01–05, the walkthrough, the cockpit demos, and the mesh `mesh-serve`/`mount-*`/`cpu`/`capsule` paths). Caveats below are real and load-bearing for honest copy.

---

### Persona 1 — Maya, the curious app developer who has never heard of Plan 9

**One-liner:** A working JS/Node developer who saw "run JavaScript outside Chrome" and "an LLM you can `cat`" and wants to *do* something in ten minutes without a CS-history lecture.

**Background.** Maya builds web apps for a living (TypeScript, React, a little Go). She has never touched Plan 9 and the words "per-process namespace" and "9P" mean nothing to her yet. She found Wanix from a talk/README line — "Plan 9 reincarnated for the age of agents" — and the part that hooked her was concrete: *JavaScript runs outside Chrome as a real sandboxed task*, and there's an *agent that fixes a broken file with approvals you click*. She is allergic to setup; if the first command doesn't print something cool, she leaves.

**Entry point.** Lands on the README or wanix.run, scans for "what can I run right now." She wants, in 30 seconds, a single copy-paste command that produces visible output — ideally the `qjs examples/qjs-demo.js` line that prints `outside Chrome: true` / `task id: 1`. She does *not* want to read AGENTS.md or the mesh blueprint first.

**Goals.**
- Run a `.js` file as a Wanix `qjs` task and see real output (`wanix qjs examples/qjs-demo.js`).
- Pass her own env/cwd/stdin/argv into a script and watch it flow through (walkthrough §2).
- Open the browser cockpit and *click* a demo — especially "Run Agent Repair Demo" — and watch a broken `broken.js` become `FIXED BY WANIX AGENT` (recipe 01).
- Build a tiny stateful thing: the `#kv`-backed counter handler, so "everything is a file" finally clicks (recipe 04).
- See the qjs→wasm→qjs duet on one shared filesystem, because "interpreted and compiled tasks share state" is a wow moment (duet demo).

**Pain points.**
- Plan 9 vocabulary as a wall: "namespace," "bind," "import/export," "9P," "factotum" with no plain-language on-ramp.
- Not knowing she needs `--wanix-services` for the cockpit demos to light up (without it `#kv`/`#agent`/qjs-shell route are simply unavailable) — this is a classic silent-failure trap.
- Assuming the cockpit agent is a *real* LLM. It is a deterministic `FakeEngine` on the served path; the real codex engine is local-trust CLI-only (`wanix agent`). Copy must say so or she'll feel misled.
- Expecting `#kv` to be durable — it's in-memory; a standalone `qjs` run resets the counter to 1 each time because `#kv` is only bound under `serve --wanix-services`.
- A Rust workspace build (`cargo run --locked --package wanix-cli`) feels heavy if she expected an `npm install`.

**How success looks.** Within her first session she has: (1) run JS outside the browser and seen `task id: 1`; (2) booted `serve --bundle workbench-fs9p --wanix-services` and clicked the agent-repair demo to green; (3) understood "everything is a file" via the `#kv` counter she can `cat` and watch increment. She can explain to a coworker "it's like Node, but every capability — storage, the LLM, the terminal — is just a file you read and write, and it runs in a tiny sandbox."

**Tone to use.** Friendly, concrete, demo-first. Lead with the command and its output, defer the theory. Translate Plan 9 terms inline ("a namespace = this task's private view of the filesystem"). Never assume prior OS-research knowledge. Be honest in a callout box about FakeEngine-vs-real and in-memory `#kv` rather than over-promising.

**Concepts she needs (in order):** Everything is a file → qjs task (JavaScript outside Chrome) → Service devices (`#name`) → `#kv` key/value device → `#agent` (an LLM as files) + approvals as files → Two tiers on one substrate (qjs + wasm) → (gentle) per-process namespaces.

**Demos she wants:** `wanix qjs examples/qjs-demo.js`; pass env/cwd/stdin/argv (walkthrough §2); `serve --bundle workbench-fs9p --wanix-services` (the cockpit); Run Agent Repair Demo; `#kv`-backed counter (recipe 04); qjs→wasm→qjs duet; Run Cockpit Self Check.

**Ideal journey through the site:**
1. 30-second hero: copy `wanix qjs examples/qjs-demo.js`, see `outside Chrome: true`.
2. "What just happened" sidebar: one paragraph on tasks + namespaces, no jargon dump.
3. Quickstart track: feed env/cwd/stdin into a script (walkthrough §2), then explicit host mount (§3) so "no ambient host authority" lands gently.
4. Boot the cockpit (`serve … --bundle workbench-fs9p --wanix-services`), with an upfront note that `--wanix-services` is what turns the demos on.
5. Click-through demos in the cockpit: Agent Repair → Duet → HTTP counter + `#kv` → Self Check, each with a "what file ops this really is" reveal.
6. First build: write her own `apps/counter.js` against `#kv` (recipe 04).
7. Honesty callouts she meets along the way: FakeEngine vs real codex; `#kv` is in-memory; freeze state with a capsule (recipe 03) when she asks "how do I keep it."
8. Soft hand-off to Persona 2 territory: "your laptop is a node — want to reach another machine?"

### Persona 2 — Devraj, the power user wiring a personal compute mesh

**One-liner:** A self-hosting infra tinkerer who runs a laptop + a home server + a cloud box and wants them to behave like one machine — mount any peer's files and devices as local, send compute to where the data lives, and let an agent operate across all of it.

**Background.** Devraj has used SSH, Tailscale, Syncthing, and NFS for years and is fluent enough in Plan 9 lore to be excited rather than confused by "the missing half of 9P." He runs things from the CLI by choice. He has read enough to know the pitch — `bind /n/<peer>` and a remote node's files *and* `#`-devices become part of his namespace; the ed25519 key *is* the address; a grant is a re-rooted subtree, not an ACL. He wants to verify it works end-to-end on his own boxes and find the exact edges before he trusts it with anything real.

**Entry point.** Goes straight to the mesh docs and recipe 02 ("Mount a remote Wanix peer and run a job on it"). He wants the two-terminal copy-paste transcript: node B `mesh-serve` prints an `iroh://…?addr=…` ticket, node A `mount-ls`/`mount-cat` reads bytes that never touched A's disk, then `cpu --node <B> -- qjs /work/build.js` runs *on B*. In 30 seconds he wants to know "is this real two-process QUIC, or a loopback demo?" — and the recipe answers that honestly.

**Goals.**
- Stand up two real nodes with persistent ed25519 identities (`~/.wanix/node.key`) and mount one from the other over iroh QUIC.
- Operate a peer's service devices as files for free: read `/n/A/#kv/<key>`, drive a peer's `#cas`, reach a peer's files — no per-service network client.
- Send a `#cpu` job to the node holding the data (reverse-export his cwd, default read-only, `--write` to opt in) — Plan 9 cpu(1) over the open internet.
- Lock down the trust boundary: default-deny grants keyed on the *verified* peer key, capability-as-bind via `SubtreeFs`, and confirm exec devices stay local-trust (`mesh-serve --wanix-services` is refused on the public endpoint).
- Freeze a built world into a CAS-backed capsule and reconstruct it byte-identical elsewhere from one hash (recipe 03).
- Run the `#agent` across machines and have two agents collaborate via `#agent/<id>/reply` / `#plumb` (recipe 05).
- Use the cockpit as an operator dashboard over it all (inspect devices, self-check).

**Pain points.**
- Mount-slot reality: shipped `mount-*` verbs bind every peer at the single `/n/remote` slot, not `/n/<peer-id>/` — per-peer prefixes are a queued follow-up. He needs this stated so he doesn't design around a path shape that isn't there yet.
- No public multi-user auth, no ethernet/vnet; the public endpoint with no `--peer`/`--grant`/`--insecure-open` is refused outright. He must not over-trust the mesh on the open internet.
- Exec devices (`#task`/`#agent`/`#cpu`) are local-trust only — `--wanix-services` is refused on the public endpoint regardless of grants. File-sharing ≠ remote code execution.
- `#cpu` v1 limits: stdout/stderr/exit arrive as a single batch *after* the guest completes (not streamed), and `CpuEvent::Cancel` stops the caller draining, not the remote computation.
- Live pub/sub edge: the serve 9P WebSocket handles one frame at a time, so a blocking `#plumb/<topic>/recv` can't interleave with a send on the same connection — live receive needs a second connection. The cockpit self-check only probes `#plumb`'s publish path.
- Not-portable surprises in capsules: live mesh peers/tickets, ephemeral fds/handles, live `#kv` device state, and symlinks/permissions are intentionally excluded — he must materialize `#kv` values into the world tree first.
- iroh is pinned to a release-candidate wave (`=1.0.0-rc.1`, blobs 0.102, gossip 0.100) and the blob plane is upstream-flagged experimental; he'll want version honesty.
- The cockpit's *mesh panel* (verified peers, GrantTable, `/n/<peer>` mounts) is not shipped yet — today the cockpit drives a single-node local serve. He'll reach for cross-peer cockpit features that aren't there.

**How success looks.** Two of his machines mount each other over QUIC; he reads a peer's `#kv` value as a file with zero device-specific code; he runs `cpu --node <peer> -- qjs build.js` and watches it execute on the data node; he installs a default-deny grant and confirms an ungranted attach gets EACCES (errno 13) while an authorized peer lands inside a `SubtreeFs` scoped to exactly the granted prefix; he freezes a world to a capsule id and restores it byte-identical on a third box; and he can articulate the boundary: "the key is the address, a capability is a bind, exec is local-trust until public auth lands."

**Tone to use.** Peer-level, precise, security-forward. Lead with real transcripts and exact CLI grammar (`cpu --node iroh://PEER?addr=… -- KIND PROGRAM [ARG…]`). Cite the enforcing tests by name where it builds trust (e.g. `parse_rejects_ungranted_public_serve`, `an_unallowlisted_peer_cannot_run_a_cpu_job`). Never overclaim: every mesh feature is recent, ADR-less, fast-moving work — frame it as proven-but-evolving, with the gaps stated plainly, not buried.

**Concepts he needs:** The missing half of 9P (import) → RemoteFs (the 9P client) → Import/export and `/n/` → Identity is the address (ed25519 = EndpointId) → A capability is a bind (default-deny grants, `SubtreeFs`, AttachPolicy) → Devices import across the mesh for free → Send the agent to the data (`#cpu`) → Capsules (ship a world by one hash) → `#plumb` (coordination, best-effort, not a queue) → One identity, two planes (9P control + iroh-blobs data) → Exec stays local-trust.

**Demos he wants:** Recipe 02 (mount remote peer + run a `#cpu` job); `/n/A/#kv` over the mesh (devices import for free); capability-is-a-bind enforced over the wire (grant → EACCES); capsule save/load round-trip with dedup + tamper-detection (recipe 03); two agents collaborate via `#agent/<id>/reply` (recipe 05); cockpit operating the device set + self-check.

**Ideal journey through the site:**
1. Mesh-recipe hero (recipe 02): the two-terminal transcript, with the upfront honesty note that `mount-*` binds at `/n/remote` and the peer-id lives in the ticket.
2. Identity primer: `~/.wanix/node.key`, the key-is-the-address model, why `Tauth` stays ENOSYS (transport authenticates the peer).
3. Devices-for-free track: read `/n/A/#kv/<key>`, drive a peer's `#cas`/files — one 9P client, every service.
4. `#cpu` exec plane: reverse-export, read-only-by-default jail, `--write`, and the stated v1 limits (batched output, no remote cancel).
5. Trust-boundary deep dive: default-deny `GrantTable` keyed on verified peer, capability-as-`SubtreeFs`, the public-endpoint refusals, exec-is-local-trust — with the gating tests named.
6. Capsules: freeze a world to a hash, restore byte-identical, dedup + integrity, and the explicit not-portable list.
7. Multi-agent + coordination: recipe 05 (`#agent/<id>/reply` delegation) and `#plumb` for cross-node handoff, with the single-frame-recv caveat.
8. Cockpit as operator dashboard, plus a "roadmap / not-yet-shipped" page (mesh panel, browser-as-peer, per-peer `/n/<peer-id>` mounts) so he plans against reality, not aspiration.

## Developer Personas — Wanix Rust-native port

These two personas are people who **build on or contribute to** Wanix. They do not just read about the vision; they open `cargo`, implement a trait, run `just check`, and submit a PR. Both need the crate map, the dependency rules, the active ADRs, the `FileSystem`/`TaskDriver`/9P contracts, the code-quality guardrails, and copy-pasteable "how to add a device/driver/transport" guides grounded in real files.

A shared hazard the IA must defuse for both: the original Go/browser Wanix is
important history, but this workspace is now Rust-native. A developer-track
landing page must say, in the first screen, "build with cargo, gate with
`just check`, and use the crate map/ADRs for ownership boundaries."

---

### Persona 1 — Priya, the Rust core contributor

**One-liner.** A systems-Rust engineer who wants to fix and extend the Wanix core crates themselves (`wanix-fs`, `wanix-vfs`, `wanix-9p`, `wanix-task`, the service devices), and needs the dependency rules, ADRs, and quality gates so her PR lands cleanly.

**Background.** 8 years of Rust, comfortable with `Arc<Mutex<…>>`, trait objects, and `cargo`. She found Wanix through the "Plan 9 reincarnated" framing and the mesh essay, cloned the repo, and ran `cargo run -p wanix-cli -- qjs examples/qjs-demo.js`. She thinks in terms of "where does this invariant live and what breaks if I move it." She is allergic to abstraction without a consumer and to PRs that get bounced on style.

**What she needs from the site.**
- The **crate map with dependency direction** as a first-class diagram, not buried in `AGENTS.md` prose — `wanix-fs → wanix-vfs/wanix-task`; `wanix-protocol`/`wanix-9p`; runtime crates pull in Wasmtime; service devices are plain `FileSystem`s over `wanix-fs`; **`wanix-mesh` is the single async/iroh edge** (tokio + iroh appear nowhere else). The "no upward dependencies" rule (`wanix-task` must not depend on `wanix-wasi`/`-qjs`/`-wasm`) needs to be stated as a hard rule with the reason.
- The **active ADR index** (0001–0005) as the canonical decision set, each summarized to its boundary: 0001 runtime ownership (Wanix owns process/fs/ns semantics, Wasmtime is substrate, no ambient host authority), 0002 the WASI task-runtime boundary + the fd-mirroring contract + the compiled-artifact-cache trust boundary, 0003 `#term`/shell lifecycle, 0004 the 9P protocol/server split, 0005 serve/handoff contracts. Plus the **ADR workflow** ("treat ADRs like code; the mesh layer has no ADRs yet — promote when contracts stabilize").
- The **`FileSystem` and `File` trait reference** (`crates/wanix-fs/src/traits.rs`): the full method set, which methods default to `NotSupported`, and the device-aware semantics — `read_ready`/`write_ready` (terminals/streams override; ADR 0003), `is_seekable` (regular files seek, service streams refuse), `content_hash` (the *only* CAS-offload hook, `Ok(None)` by default), and `confine_to_prefix` (the symlink-escape guard that `SubtreeFs` consults — no-op for opaque `MemFs`, canonicalizing for host-backed FS).
- The **code-quality guardrails** as a checklist: modules under 250 (warn) / 350 (hard) non-test lines enforced by `tools/check-module-lines.sh` against `tools/module-line-baseline.txt` (existing over-limit modules may shrink but not grow); no public raw `i32` flags/fds/rights/modes (use newtypes/builders); never hold a namespace or filesystem lock while calling into another filesystem; the required pre-commit gate is **`just check`** (fmt + module-lines + clippy `-D warnings` + test). She also wants to know the current queued cleanups (`wanix-agent/src/codex.rs` ~307, `exec_server.rs` ~283, `serve/http/app.rs` ~273 are over the warn limit).

**Pains.**
- "Which crate owns this invariant?" — she will move code, and a wrong move violates the dependency direction or a trust boundary. She needs the layering rule reachable in two clicks.
- Style/lint bounce: a PR that fails `module-lines` or `clippy -D warnings` after she's already written it. She wants the guardrails *before* she writes, not in review.
- ADR ambiguity: she needs to know when a change requires an ADR edit vs a commit message. The "if an ADR draft reads like a good commit message, keep it as the commit message" rule is exactly what she's looking for.
- Stale external assumptions from the original Go/browser implementation that do not apply to the Rust crate boundaries.

**How she arrives.** From the mesh essay or HN/Discord → README "Rust-Native Port Status" → wants `AGENTS.md`-level depth but better organized. Lands wanting "the contributor's map of the core."

**Ideal journey.**
1. Developer-track landing: "Rust-native workspace; build with cargo and use `just check`."
2. Crate map + dependency-direction diagram, with the async/iroh-confinement and no-upward-deps rules called out.
3. Active ADR index (0001–0005) each linked to its source `.md`, with the ADR workflow.
4. `FileSystem`/`File` trait reference annotated with the device-aware semantics and which methods default to `NotSupported`.
5. A worked example: read `#kv` (`crates/wanix-kv/src/lib.rs`, ~177 lines) as the canonical minimal `FileSystem` — `parse_path` → route `open` by `OpenOptions` → `read_dir` lists → mutations.
6. Code-quality guardrails checklist + the `just` recipes (`fmt`, `module-lines`, `clippy`, `test`, `check`).
7. The queued-follow-ups list as "good first cleanups."

**Success looks like.** She opens a PR that splits an over-limit module or adds a method to a core trait, it passes `just check` on the first try, and she correctly judged whether it needed an ADR touch.

**Concepts she needs.** Crate layering & dependency direction; the `FileSystem` trait; `NormalizedPath`; per-process namespaces; namespace binding/resolution; service devices (`#name`); tasks own process identity; the fd table; the 9P contract; protocol vs server split; `confine_to_prefix` / a-capability-is-a-bind; content-addressed data plane; code-quality guardrails; the ADR set + workflow.

**Demos she wants.** Run JS outside Chrome (the founding smoke test); the qjs+wasm shared-VFS differential test (`crates/wanix-cli/tests/shared_vfs_differential.rs`); `just check` green; the `#kv`/`#cas` round-trips as trait-behavior references.

**Tone.** Precise, terse, source-cited. Show the trait signature and the file path. Lead with the invariant and the reason, not the marketing. Respect that she'll read the code — point at it rather than paraphrasing it.

### Persona 2 — Theo, the integrator / extension author

**One-liner.** An engineer embedding Wanix into his own product or extending it from the edges — writing a **new service device** (a `FileSystem`), a **new task driver** (a runtime), or a **new protocol transport** — who needs the "everything is a file" extension points and the mesh-for-free payoff without having to touch the core.

**Background.** Backend/distributed-systems engineer who maintains an internal tool and wants Wanix as the substrate: a confined file-shaped capability his agents and tasks can reach. He's pragmatic — he wants the smallest trait he can implement to add value, and he wants to know what he gets for free (mesh import, 9P export, the `#task` driver auto-select) versus what he must wire himself. He's read enough Plan 9 to find "a new device is just a `FileSystem`, and it imports across the mesh for free" genuinely exciting.

**What he needs from the site.**
- **"How to add a service device"** as a guided recipe: implement `wanix_fs::FileSystem` (the `#kv` device, `crates/wanix-kv/src/lib.rs`, is the template — single-segment path parsing, snapshot-on-open reads, commit-on-`Drop` writes, `read_dir` enumeration, default-`NotSupported` mutations), keep it synchronous and iroh-free so it can live in a core crate, then bind it into the served namespace (`crates/wanix-cli/src/serve/roots.rs`, the `INSPECTABLE_SERVICE_DEVICES` source). The payoff to state up front: because it's a plain `FileSystem`, **`/n/A/#yourdevice/...` works across the mesh with zero device-specific networking**, and the cockpit's inspector renders it for free.
- **"How to add a task driver"** as a recipe: implement the tiny `TaskDriver` trait (`crates/wanix-task/src/driver.rs`) — `check()` auto-selects by program suffix (`.js`→qjs, `.wasm`→wasm), `start()` reads the module from the task's own namespace and runs it — then **register it from above** via `TaskTable::register_driver` (`crates/wanix-task/src/table.rs:48`; real call sites in `serve/roots.rs:187-191` and `agent_program.rs:76-84`). The rule he must respect: `wanix-task` is engine-free; drivers register from the orchestration layer. The shared WASI/fd builder (`wanix-wasi::task_wasi_config`) is the path both runtimes reuse if his runtime is WASI-shaped.
- **"How to add a protocol transport"** grounded in ADR 0004 and `crates/wanix-9p/src/transport.rs`: `wanix-protocol` is dependency-free codecs (`crates/wanix-protocol/src/p9/`), `wanix-9p` maps fids→`FileSystem` + Linux errnos, and **transports are thin adapters that preserve binary frame boundaries** (stdio/TCP/WebSocket/HTTP all wrap the same `P9Server`). The mirror image is `wanix-9p-client::RemoteFs` — a `FileSystem` that speaks 9P over any `Box<dyn Duplex>`, so his transport works for import too. Honest constraints he must know: `Tauth` is `ENOSYS` (identity is a transport property, not in-band); the single-connection serve handles one frame at a time (a blocking `#plumb recv` can't interleave with a write — needs a second connection); and exec devices (`#task`/`#agent`/`#cpu`) are local-trust-only and refused on the public mesh endpoint.
- The **device-contract references** for the existing devices he'll compose against: `#kv` (key/value), `#pipe` (unidirectional byte channels, EOF on last-writer drop), `#plumb` (best-effort epidemic pub/sub, *not* a durable queue), `#cas` (write-then-read-hash, BLAKE3-verified, keyspace not enumerable), `#agent` (LLM-session-as-files, approvals-as-files, served path is the deterministic `FakeEngine` not a real LLM). The blocking-stream EOF contract (`Ok(0)` only at true end; 50 ms re-check never signals EOF) is shared across all of them and he must match it.

**Pains.**
- "What's the minimum I implement?" — he doesn't want to learn the whole core to add one device. The trait surface + a copyable template is the unblock.
- Accidentally pulling tokio/iroh into a core crate, or making `wanix-task` depend on his engine — violating the layering and getting bounced.
- Overclaiming: shipping his device as "mesh-ready for untrusted peers" when exec devices are local-trust-only and there's no public multi-user auth, or treating `#plumb` like a durable queue.
- The Go-era docs again: the README "File Services" list and `CONTRIBUTING.md` suggest extension points (`#web`, `#vm`) that don't exist in the Rust port.

**How he arrives.** Searching "embed Plan 9 namespace Rust" / "9P server library Rust" / "file-shaped service for AI agents," or from the mesh essay's "the namespace is the integration layer" claim. Lands wanting "what's the extension API and what do I get for free."

**Ideal journey.**
1. Developer-track landing → "Extending Wanix from the edges (you don't need to fork the core)."
2. The three extension points side by side with their one trait each: service device (`FileSystem`), task driver (`TaskDriver`), transport (9P adapter over `P9Server`/`RemoteFs`).
3. "Add a service device" walkthrough using `#kv` as the template, ending at binding into the served namespace + the mesh-for-free + cockpit-inspector payoff.
4. "Add a task driver" walkthrough: `check`/`start`, register-from-above, the shared `task_wasi_config` if WASI-shaped, the auto-select-by-suffix behavior.
5. "Add a transport" walkthrough: protocol-vs-server split, frame-boundary rule, `RemoteFs` for the import side, and the honest constraints (`Tauth` ENOSYS, single-frame serve, local-trust exec).
6. Device-contract reference cards for `#kv`/`#pipe`/`#plumb`/`#cas`/`#agent` with the shared blocking-stream EOF contract and the "don't overclaim" caveats.
7. Layering rules + `just check` so his crate fits the workspace.

**Success looks like.** He adds a new `FileSystem`-backed device in its own synchronous, iroh-free crate, binds it via `serve --wanix-services`, mounts it from a second node at `/n/<peer>/#hisdevice`, and sees it round-trip over the mesh and render in the cockpit inspector — all without modifying a core crate.

**Concepts he needs.** Everything-is-a-file; the `FileSystem` trait; service devices (`#name`); task drivers + register-from-above; the 9P contract; protocol vs server split; import/export and `/n/`; devices import across the mesh for free; a-capability-is-a-bind; the blocking-stream EOF contract; identity-is-the-address; the local-trust-only exec boundary; crate layering & async/iroh confinement.

**Demos he wants.** The `#kv` device as a `FileSystem` template; create/control a child task via `#task`; mesh import across two processes (`serve --p9` raw-TCP door + `mount-ls`/`mount-cat`/`mount-write`); a device imported for free over the mesh (`/n/A/#kv/...`); `#cas` write-then-read-hash round trip; `#pipe` Unix-pipe composition; the cockpit service inspector rendering a device.

**Tone.** Pragmatic and payoff-forward. Lead with "here's the one trait and here's what you get for free," then the honest constraints so he doesn't overclaim. Copy-pasteable code paths and real file references, minimal philosophy unless it changes what he builds.
